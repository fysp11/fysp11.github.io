## 2025-03-02 - Secure Error Handling in Serverless API Routes
**Vulnerability:** API endpoints under `src/pages/api/` (such as `ai-chat.ts`, `ai-image.ts`, `google-chat.ts`, and `tts.ts`) were returning detailed error strings to the client via `catch` blocks or invalid states. Specifically, things like missing configurations, raw upstream provider error messages, raw fallback payloads, or native exception messages (e.g. `error.message`) were leaked over the network in JSON responses.
**Learning:** Exposing detailed upstream API error messages, stack traces, or fallback data objects introduces a security risk (Information Exposure). An attacker could leverage these leaked implementation details (like missing specific env variables or upstream structure responses) to map out application components, underlying services, or even manipulate payloads accordingly. The failure existed due to returning `error.message` or raw error structs directly in the `Response` instead of genericizing them for external viewers.
**Prevention:** Always log the verbose/actual error server-side (using `console.error`) for debugging, but only ever return a generic, sanitized error payload (e.g. `{ error: "Internal error" }`) to the client. This implements the "Fail securely" principle from the Sentinel philosophy.
